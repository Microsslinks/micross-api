# 一个客户挂多个折扣方案 —— 现状调研与改造方案

> 立项：2026-09-14（业务方原话：**"一个客户不能只绑定一个折扣方案，必须可以绑定多个折扣方案，否则一个客户得注册很多用户，这简直是疯了。"**）

## 一、一句话结论

表结构**本来就允许**一个客户同时挂多条打折绑定（同一个人可以绑 N 个不同方案），卡住这件事的不是数据库，而是两处：**算钱的时候只读了一个方案**（`users.discount_plan_id` 是单值快路径），**界面上三处都做成了单选**。

所以改造量比预想小。但开工前必须先定死一条规则，否则算不了钱：**同一个模型同时被两个方案说到时，用谁的价**。

## 二、现状：一个客户的价是怎么定出来的

### 2.1 三张表 + 一个快路径列

| 名字 | 位置 | 装什么 |
|---|---|---|
| `discount_plans` | `model/discount.go:47` | 折扣方案：归属（平台／经销商）、基础折扣、最低折扣、计费模式、分成比例、启停状态 |
| `discount_rules` | `model/discount.go:93` | 方案里的模型级／厂商级覆盖（比基础折扣更具体的那一层） |
| `discount_bindings` | `model/discount.go:452` | **"谁、在什么时间段、用哪个方案"**：主体、方案 id、生效起止、来源、状态 |
| `users.discount_plan_id` | `model/user.go:99` | 绑定表的快路径冗余。**`int` 类型，只能放一个方案 id**，每次绑定变化时由 `syncUserDiscountPlanId`（`model/discount.go:386`）重算 |

### 2.2 现在往客户身上写绑定的三个地方

1. **平台手工定价** —— 用户列表 → 行菜单「设置专属折扣」→ `POST /api/discount/admin/bindings`，来源记 `manual`（`controller/discount.go:465`）。
2. **客户号** —— 客户拿经销商发的号绑自己，落一条来源 `customer_code` 的绑定（`model/agent_customer.go:179`）。
3. **经销商定价** —— 控制台 → 我的客户 → 设置价格，落一条来源 `agent` 的绑定；**写入前会先把自己上次定的价撤掉**（`model/agent_customers.go:224`），所以经销商也挂不了第二套。

来源优先级写在 `model/discount.go:431`：`manual > agent > subscription > customer_code > migration`。

### 2.3 算钱怎么读（全世界只有这一份折扣口径）

`model/discount_billing.go:44` 的 `ResolveBillingDiscount` → `model/discount_resolve.go:36` 的 `ResolveUserDiscount`：

- 第一步：读 `users.discount_plan_id`，**只拿到一个方案**（`model/discount_resolve.go:55`）。
- 第二步：在这个方案里找，模型级规则 → 厂商级规则 → 方案基础折扣（`model/discount_resolve.go:92`）。
- 第三步：如果这个人自己是经销商，拿"他的拿货价"和方案价比一次，**取便宜的**（`model/discount_resolve.go:124`）。

这一份结果被三处共用：实际扣费（`relay/helper/discount.go:17` 把折扣乘进分组倍率）、试算、保存前校验。原设计把"折扣口径只能有这一份"写进了注释，改造时这条原则不能破。

### 2.4 界面上三处都是单选

- 用户列表 → 行菜单 → 「设置专属折扣」：一个下拉选一套方案，文案里直书 "One customer follows one plan at a time."（`web/src/features/users/components/dialogs/set-discount-dialog.tsx:242`）
- 折扣方案页 → 「绑定客户」抽屉：文案 "binding replaces the previous one"（`web/src/features/discounts/components/discounts-bindings-drawer.tsx:275`）
- 控制台 → 我的客户 → 「设置价格」：单选一套，请求体就是 `{ plan_id }`（`web/src/features/dealer/` 的 `agent-customers-panel.tsx:380` + `dealer/api.ts:126`）

## 三、今天会发生什么（"只能多开账号"的根源）

举个真实会遇到的例子。客户"某某科技"身上有三套说好的价：

- 平台给的企业 VIP：**方案 A**，GPT 系列 8 折（模型级规则），其余模型 95 折（基础折扣）
- 经销商跟他谈的：**方案 B**，Claude 系列 9 折（模型级规则）
- 客户号签的：**方案 C**，全部模型 95 折

现在的结果：`pickActiveDiscountBinding`（`model/discount.go:404`）**在整用户层面**挑一条生效，只看来源，不看这个方案对当前模型有没有说法。于是：

- 方案 A 因为来源是 `manual` 胜出，方案 B、C **形同不存在**；
- 调用 Claude 时，不会去比方案 B 的 9 折，而是落回方案 A 的基础折扣 95 折——**谈好的价静默失效**；
- 界面上还堂堂正正显示"生效方案 = 方案 A"，看不出丢了一套价。

客户想拿到谈好的那套价，只能**再注册一个账号**专门跑 Claude。这就是"疯了"的根源。

> 现存唯一会"两套价比一比"的地方，是经销商本人消费时的拿货价 vs 方案价。平台给客户定的价、经销商给客户定的价、客户号签的价，三者之间**从不比较**，只按来源排队。

## 四、改造方案

### 4.1 裁决规则（推荐）

一句话：**对某个模型，谁把话说得更具体就用谁的价；一样具体看是谁定的；都一样定就看谁便宜。**

按顺序比五层：

1. **各自解析**：把这个人身上所有生效绑定（未停用、在生效期内）逐个解析出"对这个模型的折扣"，同时记下这个折扣是**模型级规则 / 厂商级规则 / 方案基础折扣**里的哪一档。
2. **比具体度**：有人给了模型级规则，就只在这些方案里挑；没人给就比厂商级；都没有才比基础折扣。
3. **具体度相同**：比来源优先级（`manual > agent > subscription > customer_code > migration`）。
4. **来源也相同**：取更便宜的那条（对客户有利）。
5. **仍然相同**：取最新那条绑定。最后再与经销商的拿货价比一次便宜（**这一层保持现状不动**）。

算例（客户"某某科技"调 `claude-sonnet`）：

| 方案 | 来源 | 对 Claude 的说法 | 落到哪一档 |
|---|---|---|---|
| 方案 A（平台） | manual | 只有基础折扣 0.95 | 基础折扣 |
| 方案 B（经销商） | agent | 模型级规则 0.90 | **模型级** |
| 方案 C（客户号） | customer_code | 只有基础折扣 0.95 | 基础折扣 |

→ 第 2 层就把方案 A、C 淘汰了（它们只是基础折扣），答案 **0.90，来自方案 B 的模型级规则**。

调 `gpt-4o` 时：方案 A 有模型级规则 0.80，方案 B 没有模型级规则 → 答案是 **0.80，来自方案 A**。

这套规则的解释力最强，和现在"方案内部优先模型级规则"（`pickDiscountRule`）的思路是同一套，只是从"方案内"扩展到"方案之间"。

### 4.2 两条备选规则（不推荐／可选）

- **一律取最便宜**：所有生效绑定解析完直接取最小值。实现最简单，但**平台专门给某个模型定的价会被一条旧的通用绑定顶掉**，事后无法解释"这个价怎么来的"，也没法表达"这套价只管这几个模型"。
- **方案上标注"只管哪些模型"**：给方案加一条"适用范围"（比如方案 B 只管 `claude-*`），命中范围才有资格参与比较。这跟推荐规则不冲突，将来想要更硬的分区再加。

### 4.3 把话说透：什么情况才"必须"多方案

如果只想要"一堆价里挑个便宜的"，其实**用不着多方案**——在同一个方案里多写几条模型级规则就等价了。真正非多方案不可的只有两种情况：

1. **两套价来自不同的人，谁都改不了对方的方案**。经销商改不了平台方案，平台也不该去改经销商方案；客户号签的价更不能被后手抹掉（现在就是靠"并存两条主张"做到的，见 `model/agent_customers.go:235` 的注释）。
2. **将来订阅／免费与按量并存**。订阅方案管住的模型不收费、其余按量打折——这天然是"两套方案同时生效"，现在 `billing_mode` 只在界面上记录、不参与计算（`web/src/features/discounts/components/discounts-plan-mutate-drawer.tsx:388`）。

**这两点里你要的是哪个（或都要），决定实现难度与界面形态**，见第七节第 5 问。

### 5.2 前端（四处要改、一处要删文案）

1. **用户列表 → 行菜单 → 「设置专属折扣」**：单选下拉 → 已挂方案列表 + 追加 + 逐条解绑，每行显示来源与生效期（现在只有单选和一句"一次只能一个"的提示）。

5. **i18n**：删／改 "One customer follows one plan at a time." 及其简繁词条。

### 5.3 上线顺序（重要）

折扣计费总开关已于 2026-09-13 打开，**口径一变就直接影响真实扣费**。建议：

1. 先做"多绑定读取 + 裁决"的**纯读取逻辑与测试**。此阶段行为与现状一致（现在每个人至多一条生效），零风险。
2. 再放开界面多选（此时才可能出现一个人身上多条同时生效）。
3. 放开前**跑一次存量扫描**：列出"有效绑定 ≥ 2 条"的客户，逐个确认期望价——现在存量应该都是 1 条，但不排除历史数据。
4. 若仍有担心，改造期间临时关掉总开关，上线后再打开。

## 六、风险

- **计费热路径的查询次数**：从现在的 2~3 次（用户 → 方案 → 规则）变成 3~4 次（用户 → 绑定 → 方案 → 规则）。必须批量查询，**绝不能写成逐条查**，否则一单几十次数据库往返。
- **解释性**：现在消费日志只记一个 `discount_plan_id`（`service/log_info_generate.go:121`）。多方案后要能回答"为什么是这个价"——建议日志里同时记下落选的候选方案与落选原因（具体度／来源／价格）。
- **试算与保存前校验漏报**：只校验生效那条，会漏掉"另一条绑定其实会亏本"。
- **静默改价**：见 5.3 第 3 步。这是本项目一贯的红线（不打折的请求要与改造前逐笔一致）。

## 七、口径拍板（2026-09-14，业务方已确认）

1. **裁决规则**：用第四节推荐的那条——**谁说得更具体 → 谁定的 → 谁便宜 → 谁新**（业务方确认"便宜排在谁拍板之后"）。
2. **平台手工定价与经销商定价谁压谁？** ⚠️ **唯一遗留问题**。现在的硬门槛是：平台一旦给某个客户单独定过价，经销商**完全不能**再给这个客户定价（`model/agent_customers.go:194`）。多方案下我的建议是**放宽为"按模型竞争"**：去掉入口处的全局禁止，冲突交给裁决算法——同一个模型、同具体度时平台特批赢经销商（来源 `manual > agent`），但经销商在别的模型上仍能定价（这正是"平台管 GPT、经销商管 Claude"的场景）。**待你确认**。这条不挡第一步（纯读取改造）。
3. **一个客户最多挂几套：10 套**（不是 5 套）。
4. **经销商只能挂自己货架上的方案**：确认。且已拍板经销商**不开"自己组价"**，就是转卖平台方案——多方案对经销商的形态是"从货架挑多套、逐条挂逐条撤"。
5. **要的是"按模型分区定价"**（这套价管这几个模型、那套管另外几个）：从业务方给的场景（5 个模型套 3 个方案、挂在同一个用户身上）已确认。单纯"多套挑便宜"用不着多方案。
