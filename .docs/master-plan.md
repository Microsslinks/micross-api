## 一、改造目标

### 1.0 一句话

把一个"**单一平台 + 统一价格 + 全局分组**"的 API 网关，改造成"**可以分层卖 API 的分销平台**"。

### 1.1 业务目标（业务方原话，不加工）

**四类客户**：个人用户与工作室 / 中小企业 / VIP 客户 / 经销商。

**三种价格模式**：

1. **官方价格**作为基准
2. **客户价格管理体系**——以官方报价为基准形成折扣（100% / 九折 / …… / 两折 / 免费 / 定制）；并支持**订阅模式**（订阅量决定折扣水平）
3. **经销商价格：差价模式**——经销商低价进货、管理下属、自定零售折扣、可发 VIP 客户号（可代注册，也可客户自注册）
4. **佣金模式**——每个客户都可邀请客户形成佣金；**不能赔本**；只冲钱包、**不可提现**
5. **价格管理模式**——以客户为中心；可按客户、按厂商、按模型定制折扣
6. **定向问题**：同一模型多供应商报价不同（Kimi-K3：A 50% / B 55% / C 56%），给客户 55% 时必须保证**不会调用 B 和 C**

### 1.2 价格体系：全案的锚

| 层 | 名称 | 定义 | 由谁决定 |
|---|---|---|---|
| L1 | **官方标价** | 模型基准价，每 1M tokens 的官方报价 | 平台 |
| L2 | **采购成本** | `L1 × 渠道成本折扣` | 上游谈判 |
| L3 | **批发价** | `L1 × 经销商折扣` | 平台给经销商 |
| L4 | **零售价** | `L1 × 客户折扣` | 经销商 / 平台给客户 |

**基准铁律（D8）**：L1 是唯一出发点，L2/L3/L4 全是它的折扣派生。

> **L1 口径已定（2026-09-12）**：L1 以**厂商官网价**为准，不采用"系统内人工维护的倍率价"。代价是需补一套"官网价 → 倍率"的映射与同步机制（厂商 API 不提供定价接口，现有"上游价格同步"为手动、一次性、不追踪）。该机制**不阻塞 P1**（折扣只做乘法，可用现状倍率价跑通），但 **P2 引入渠道成本前必须落地**。
**不赔本铁律**：`采购成本折扣 ≤ 批发价折扣 ≤ 零售价折扣`，任一层击穿即为亏损。

> 这两条铁律派生了全案：折扣档位、经销商差价、供应商定向、无渠道兜底，全部是它们的推论。

### 1.3 五个核心结论

| # | 结论 | 含义 |
|---|---|---|
| 1 | **折扣制度取代分组倍率** | 全局共享的 `GroupRatio` 无法承载"以客户为中心"的定价，必须换掉 |
| 2 | **成本成为一等公民** | 渠道增加"进货折扣"属性，与售价折扣共同构成路由与计费依据 |
| 3 | **三段式价格** | 成本价 ≤ 批发价 ≤ 零售价 |
| 4 | **不赔本前移到选渠道环节** | 路由时就过滤掉会亏本的渠道（这同时是定向问题的答案） |
| 5 | **收益只能内部循环** | 佣金与经销商收益进额度账户，只能消费，不可提现 |

### 1.4 判定标准：可理解性优先（D10，总纲）

**一句话**：对外只有两个词——**官方价**与**折扣**。实现层概念（quota、倍率、比例、分组）不进业务语言。

**三角色自测**（任一角色答不上来，即为模型缺陷）：

| 角色 | 必须能自己回答 |
|---|---|
| 客户 | 这次花多少钱？为什么是这个价？怎么才能更便宜？ |
| 经销商 | 我进价多少？最低能卖多少？我能赚多少？ |
| 运营 | 这单赚了吗？亏在哪里？要不要调？ |

**判据**：讲不清**不是文案问题，是模型问题** → 改模型，不是改文案。

3. 方案基础折扣 discount_plans.base_discount
4. 系统默认     1.0

- 供给侧真实形态：**一个厂商可有多条上游供应商线路**（如 OpenAI 同时走"微观互联 2.7 折"与"某某 2.5 折"），**每条线路只供一个厂商**的模型；

## 六、前后端协调关系

> 这一节是全案的**执行纪律**。改造跨越 6 期、涉及计费链路，协调机制比技术方案更决定成败。

### 6.1 总原则：契约先行，契约冻结后才各自开工

所有**跨端字段**先在 `06-api-and-ui.md` 定死（路径、请求/响应结构、错误码、字段可见性），然后：

- 后端按契约实现并写测试
- 前端按契约建页面，**接口未就绪时用 mock**

**禁止**：后端先实现、前端再猜。这会产生"前端按字段名猜语义"的经典错配（如 `sell_ratio` 到底是折扣还是加价）。

### 6.2 并行边界靠「默认值」，不靠「排期」

这是让前后端真正能并行的关键设计：

```
折扣因子默认 1.0  →  未绑定方案的用户，计费结果与改造前完全一致
```

由此得到：

| 阶段 | 后端 | 前端 | 是否并行 |
|---|---|---|---|
| G0 影子 | 建表 + 折扣 CRUD（**不接入计费**） | 折扣方案管理页可读写 | ✅ 完全并行 |
| G1 内部 | 接入折扣因子，开关只对内部账号开 | 页面继续完善，**不改字段** | ✅ 并行 |
| G1 验收 | **逐笔金额比对**（绑定 1.0 必须与改造前一致） | —— | ⏸ **串行卡点** |
| G2 起 | 逐级放量 | 只做体验优化 | ✅ 并行 |

> 唯一的串行卡点是 **G1 逐笔比对**。它通过之前，不要进入 P2。

### 6.3 三个交接点（双方必须同时在场的时刻）

| # | 交接点 | 冻结内容 | 通过标准 |
|---|---|---|---|
| 1 | **契约冻结** | 接口签名、字段语义、字段可见性分级、错误码 | 双方对同一份 `06` 文档签字确认 |
| 2 | **影子验证**（G0 末） | CRUD 可用、页面可读写、计费未接入 | 前端能完整走通"建方案 → 绑用户 → 试算" |
| 3 | **计费切换**（G1 末） | 折扣解析优先级、日志字段 | **逐笔比对通过**；此后字段不再变更 |

### 6.4 纪律一：前端不自己算折扣

**这是最容易翻车的一条。**

| 做法 | 后果 |
|---|---|
| ❌ 前端拉 `discount_plans` 自行计算命中折扣并展示 | 出现第二套折扣解析实现，与计费**必然**不一致（优先级规则、有效期、缓存都会偏离） |
| ✅ 前端展示**官方价**（静态）；客户实际折扣由后端接口下发 | 单一实现，前后端永远一致 |

**落地**：后端提供有效的客户折扣（随用户信息或专用接口），前端只做 `官方价 × 折扣` 的**纯展示乘法**，不做规则解析。

### 6.5 纪律二：敏感字段由后端剥离，前端不做"藏起来"

| 字段 | 处理 |
|---|---|
| `cost_ratio`（渠道成本） | 仅 `AdminAuth` 可见（商业机密） |
| `admin_info`（含 `sell_ratio` / `cost_ratio` / `cost_breach`） | **后端剥离**，普通用户视角看不到 |
| 分组、倍率 | 客户侧**后端不下发**，而非前端隐藏 |

**理由**：前端隐藏是可绕过的（打开 DevTools 就能看到响应体）。凡"客户不可见"的东西，必须在响应体层面就不存在。

### 6.6 纪律三：术语与文案单一来源

| 项 | 唯一来源 |
|---|---|
| 术语对照表 | `06-api-and-ui.md` §4.6（官方价 / 折扣 / 余额 / 花费 / API Key / 调用记录 / 套餐 / 推广佣金 / 经销商） |
| 前端文案 | `web/src/i18n/locales/{en,zh,zh-TW,fr,ru,ja,vi}.json`，key 为**英文原文** |
| 后端文案 | `i18n/`（go-i18n，en / zh） |

**规则**：新增术语先进 §4.6，再落 i18n。**改 value 不改 key**，改完执行 `bun run i18n:sync`。
**禁止**：出现需要 tooltip 或一段解释才能讲明白的元素（D10）——先默认删除。

## 九、红线与风险

### 9.1 不可突破的红线

- 上游保护信息（`new-api` / `QuantumNous` 品牌、署名、LICENSE、Go module path）**不得改动**
- 计费安全不变量：额度运算不得因溢出或未校验输入产生负数
- `relaykit/` 必须独立可构建
- JSON 统一走 `common.Marshal` / `Unmarshal`
- 数据库三兼容（SQLite / MySQL ≥ 5.7.8 / PostgreSQL ≥ 9.6）
- `.docs/` 不进入 Git

### 9.2 致命风险

| # | 风险 | 对策 |
|---|---|---|
| **R1** | **选渠道过滤漏了某条旁路**（重试 / 粘连 / auto 分组） | 过滤逻辑**唯一实现** + 三处调用覆盖 + 专项验证 |
| **R6** | 折扣低于成本后大量调用导致亏损扩大 | 保存期校验 + 运行期过滤 + 成本击穿告警（双保险） |
| R8 | 改动计费链路引发既有功能回归 | 折扣因子默认 1.0 + G1 逐笔比对 + 逐级灰度 |

### 9.3 高风险项

| # | 风险 | 对策 |
|---|---|---|
| R2 | 折扣精度导致账单尾差 | `decimal(10,6)` 存字符串，禁 `float` |
| R3 | 渠道成本未配置 → 折扣客户无渠道可用 | 渠道列表显著警示 + `cost/stale` 接口 + 灰度期人工核对 |
| R4 | 缓存与 DB 不一致 | 按 `plan_id` 失效缓存（参照 `InvalidatePricingCache`） |
| R7 | 三库迁移在某方言上失败 | 避免复杂约束 + 三库各跑一次 |

### 9.4 回滚（靠开关，不靠改代码）

| 层级 | 动作 | 影响 |
|---|---|---|
| L1 功能级 | 关「折扣因子」开关 | 计费回 `GroupRatio` 路径，立即生效 |
| L2 数据级 | 解绑全部 `discount_bindings` | 折扣失效，方案数据保留 |
| L3 路由级 | 关「成本过滤」开关 | 恢复原路由（**会重新产生亏损风险，仅紧急使用**） |
| L4 结构级 | 保留新表新字段不删 | 空置即可 |
